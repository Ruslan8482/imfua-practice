## 🎯 1. Цель

Нормализовать до 3NF таблицу с заголовками
«Код заказа | Дата | Код клиента | Код товара | Название товара | Цена | Код представителя | Имя представителя | Количество»,
соблюдая условие задания: **один код заказа должен соответствовать только одному представителю**.
Клиента ведём по коду заказа, товары — по коду товара.

## ⚠️ 2. Допущение по данным

**В исходном задании приведена только структура таблицы, строки не заданы; ниже использован демонстрационный набор данных, схема и правила 3NF соответствуют условию.**

Набор строк ниже составлен в том же стиле, что и данные лабораторных № 1/№ 2: коды заказов
6001–6004, клиенты 301–303, товары 401–405, представители 901–903, даты 2026 года.
В заголовках оригинала нет имени клиента, поэтому справочник `clients` содержит только код.

### Нарушения

1. **Повторяющиеся группы.** Дата заказа, клиент и представитель повторяются в каждой строке товара.
2. **2NF.** Ключ — `(order_id, product_id)`; `order_date`, `client_id`, `rep_id`, `rep_name` зависят только от `order_id`, а `product_name`, `price` — только от `product_id`.
3. **3NF.** Транзитивные зависимости: `product_id → product_name, price`, `rep_id → rep_name`.
4. **Аномалии:**

| Аномалия | Что происходит в «плохой» таблице | Как исправляется в 3NF |
|----------|-----------------------------------|------------------------|
| Обновления | Смена имени представителя в одной строке заказа 6001 даёт заказу двух разных представителей, нарушая условие | Представитель хранится один раз в `representatives`, ссылка — один раз в шапке `orders` |
| Удаления | Удаление всех строк заказа 6004 стирает клиента 303 и представителя 903 из базы | Клиент и представитель остаются в своих справочниках |
| Вставки | Нельзя добавить представителя без заказа, не создав строку с `NULL` в полях товара | `INSERT INTO representatives (...)` работает без заказов |

## 3. Целевая схема (3NF)

| Таблица | Назначение | Ключ |
|---------|-----------|------|
| `clients` | коды клиентов (`client_id`) | PK `client_id` |
| `representatives` | представители (`rep_id`, `rep_name`) | PK `rep_id` |
| `products` | товары (`product_id`, `product_name`, `price`) | PK `product_id` |
| `orders` | шапки заказов (`order_id`, `order_date`, `client_id`, `rep_id`) | PK `order_id`, FK → `clients`, `representatives` |
| `order_items` | позиции (`order_id`, `product_id`, `quantity`) | PK `(order_id, product_id)`, FK → `orders`, `products` |

Пять таблиц вместо четырёх: дополнительный справочник `representatives` необходим,
иначе останется транзитивная зависимость `order_id → rep_id → rep_name`. Хранение `rep_id`
только в шапке заказа гарантирует условие «один заказ — один представитель».

## 📊 5. Результаты проверок (реальный запуск)

| Проверка | Ожидаемое значение | Фактический результат |
|----------|--------------------|------------------------|
| `SUM(price * quantity)` до нормализации | 66 500.00 | `total_old = 66500.00` |
| `SUM(p.price * oi.quantity)` после нормализации | 66 500.00 | `total_new = 66500.00` |
| Заказов: `DISTINCT order_id` / `COUNT(*) FROM orders` | 4 / 4 | `old_orders = 4`, `new_orders = 4` |
| Клиентов: `DISTINCT client_id` / `COUNT(*) FROM clients` | 3 / 3 | `old_clients = 3`, `new_clients = 3` |
| Товаров: `DISTINCT product_id` / `COUNT(*) FROM products` | 5 / 5 | `old_products = 5`, `new_products = 5` |
| Представителей: `DISTINCT rep_id` / `COUNT(*) FROM representatives` | 3 / 3 | `old_reps = 3`, `new_reps = 3` |
| Позиций: исходных / `COUNT(*) FROM order_items` | 7 / 7 | `old_items = 7`, `new_items = 7` |
| «Сколько потратил клиент 301?» | 40 500.00 | `301	40500.00` |
| Представителей на один заказ | `COUNT(DISTINCT rep_id) = 1` для каждого `order_id` | `6001 → 1`, `6002 → 1`, `6003 → 1`, `6004 → 1` (`reps_per_order`) |
| Аномалии после 3NF | representative меняется в одной строке; клиент/представитель без заказа возможны | В «плохой» таблице заказ 6001 даёт `901	Петрова Мария` и `901	Иванов Иван`; в `representatives` после `UPDATE` одна строка `901	Петрова Мария`, заказ снова `6001	901	Петрова Мария`; после удаления заказа 6004 клиент `303` и представитель `903	Сидоров Алексей` остаются; `904	Новый представитель` добавлен без заказа |
